# HLS Spatial Verification

**Can these memory accesses run in the same clock cycle?** This tool answers
that question for hardware generated by High-Level Synthesis (HLS), and proves
the answer instead of guessing.

It is an LLVM pass plugin that implements the method from the paper
[*Separation Logic for Memory Conflict Detection in High-Level Synthesis*](https://doi.org/10.48550/arXiv.2607.07126)
([citation below](#citation)).

## The problem in one picture

When HLS turns a loop into hardware, it often **unrolls** it: four iterations
become four copies of the loop body that should run side by side. If those
copies read from the same array, they all need memory at the same time.

On-chip memory (SRAM) usually has **one port per bank**: it can serve only one
access per cycle. So HLS tools **partition** an array into several banks:

```
cyclic partitioning, N = 4 banks         element e lives in bank  e mod 4

  bank 0:  A[0]  A[4]  A[8]  ...
  bank 1:  A[1]  A[5]  A[9]  ...
  bank 2:  A[2]  A[6]  A[10] ...
  bank 3:  A[3]  A[7]  A[11] ...
```

Now `A[i]`, `A[i+1]`, `A[i+2]`, `A[i+3]` can be read in one cycle, **if** they
really land in four different banks. With only 2 banks, `A[i]` and `A[i+2]`
both land in bank 0 and collide.

For simple indices this is easy to check by eye. For indices like `x*y`,
`(x*y) mod 7`, multi-dimensional arrays, vector loads or code inside `if`
branches, it is not. A wrong "yes" means **broken hardware**; a needless "no"
means **slow hardware**.

## What the tool does

The tool runs on LLVM IR **after loop unrolling** and, for every group of
accesses that would run together, does the following:

1. **Finds every memory access** (load, store, atomic, memory-touching call)
   and works out which element it touches, directly from LLVM's address
   arithmetic (`getelementptr`).
2. **Computes the bank** of each access from the array's partitioning
   (*cyclic*, *block* or *complete*).
3. **Asks the Z3 SMT solver** whether any two accesses could ever hit the same
   bank, for *any* possible input values, using exact machine arithmetic
   (including integer overflow).
4. **Gives a verdict:**

   | Solver result | Status | Meaning | Schedule |
   | --- | --- | --- | --- |
   | No collision is possible | **Proven** (paper: *Sat*) | Safe to overlap | **Parallel** |
   | A collision was found | **Refuted** (paper: *Unsat*) | Prints the example input that collides | Sequential |
   | Solver ran out of budget | **Timeout** (paper: *Tout*) | Undecided | Sequential |
   | Anything else unclear | **Unknown** | Undecided | Sequential |

**The tool is conservative by design.** It says *Parallel* only when it has a
proof. Whenever it is unsure, the answer is *Sequential*: the hardware is then
slower but always correct.

In the paper's terms, each access *claims* a bank; the claims must be
*separate* (the separating conjunction of Separation Logic), and owning the
same bank twice is a contradiction. See §3–§6 of the paper for the formal
model and the soundness proof.

## Installation

You need:

| Tool | Version |
| --- | --- |
| LLVM (with `opt`, and `FileCheck` for tests) | 17, 18, 19 or 20 (developed on 18) |
| Z3 (C++ API) | 4.8 or newer |
| CMake | 3.20 or newer |
| Ninja | any |
| lit (only for tests) | `pip install lit` |
| A C++17 compiler | the one that built your LLVM is best |

### Linux (Ubuntu / Debian)

```sh
sudo apt install llvm-18-dev llvm-18-tools clang-18 libz3-dev cmake ninja-build
pip install lit

cmake -S . -B build -G Ninja -DLLVM_DIR=/usr/lib/llvm-18/lib/cmake/llvm
cmake --build build
```

### macOS (Apple Silicon) with conda

Using one conda environment keeps LLVM, the compiler and the C++ runtime
consistent with each other:

```sh
CONDA_SUBDIR=osx-arm64 conda create -n hls-sv -c conda-forge --override-channels \
    llvmdev=18 llvm-tools=18 clangxx=18 'libz3=4.16' cmake ninja lit
conda activate hls-sv          # or: export PATH=<env>/bin:$PATH

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_COMPILER=$CONDA_PREFIX/bin/clang++ \
  -DCMAKE_PREFIX_PATH=$CONDA_PREFIX \
  -DLLVM_DIR=$CONDA_PREFIX/lib/cmake/llvm \
  -DCMAKE_OSX_SYSROOT=$(xcrun --show-sdk-path) \
  -DCMAKE_MODULE_LINKER_FLAGS="-L$CONDA_PREFIX/lib"
cmake --build build
```

> **Why `-L$CONDA_PREFIX/lib`?** It makes the plugin use the same C++ runtime
> (`libc++`) as conda's `opt`. Without it, two different runtimes end up in
> one process.

Either way, the result is the plugin **`build/HLSSpatialVerify.so`**.

## A first run

The repository ships small example programs in `tests/lit/`. Try the two
"twins" below. They contain the same loop; only the number of banks differs.

```sh
opt -load-pass-plugin build/HLSSpatialVerify.so \
    -passes='print<hls-spatial-verify>' -disable-output tests/lit/cyclic_ok.ll

opt -load-pass-plugin build/HLSSpatialVerify.so \
    -passes='print<hls-spatial-verify>' -disable-output tests/lit/cyclic_conflict.ll
```

(On Ubuntu the tool may be called `opt-18`.)

The loop body, written as C, is:

```c
int A[64];                     // cyclic partitioning: 4 banks, then 2 banks
for (int i = 0; i < 64; i += 4)
  sum += A[i] + A[i+1] + A[i+2] + A[i+3];   // loop unrolled 4 times
```

* With **4 banks** the result is `Proven (paper: Sat) -> Parallel`.
* With **2 banks** the result is `Refuted (paper: Unsat) -> Sequential`, and
  the tool shows *why*: with `i = 0`, `A[0]` and `A[2]` both sit in bank 0.

## Reading the output

Here is the 2-bank result, annotated:

```
HLS spatial verification: @sum                       <- the function
  group #0  region: loop %loop                       <- accesses that run together
    @A: Gamma = (alpha=0, M=64, cyclic), N=2, elem=4B
         ^ array A: 64 elements of 4 bytes, cyclic, 2 banks
    cfu(E, A, N) = *_i bank(k_i, A, N) over 4 claim(s):
      [0] %v0 = load i32, ptr %p0, align 4           <- access #0
          expr = %i    k = ...                        <- element index, bank index
      [1] ...
    status: Refuted (paper: Unsat)  ->  Sequential    <- the verdict
    reason: counterexample for claims #0 and #2: both claim bank #x0...0
            (offsets #x0...0 and #x0...2) when {%i = #x0...0}
    VC matrix  (A_i & A_j => k_i != k_j):  '.' proven  'X' conflict  '?' unknown  'T' timeout
           0  1  2  3
        0  -  .  X  .                                 <- #0 collides with #2
        1     -  .  X                                 <- #1 collides with #3
        2        -  .
```

Tips:

* Numbers such as `#x0000000000000002` are 64-bit hexadecimal: here, `2`.
* The `k = ...` expressions can look strange (`concat`, `extract`). That is
  just Z3's way of writing `e mod 4` as "the lowest two bits of `e`".
* The **matrix** shows every pair of accesses: `.` means "can never collide",
  `X` means "can collide" (with an example below the matrix).
* `region: function top level` means the accesses are not inside a loop.
* `<unresolved base>` groups accesses whose target array could not be
  determined. They are always Sequential.

## Telling the tool how your arrays are partitioned

### In the IR (metadata)

Attach `!hls.partition` to a global variable or an `alloca`:

```llvm
@A = global [64 x i32] zeroinitializer, !hls.partition !0
%T = alloca [16 x float], align 4,       !hls.partition !1

!0 = !{!"scheme", !"cyclic",   !"factor", i32 4}   ; 4 banks, e mod 4
!1 = !{!"scheme", !"complete"}                     ; one register per element
```

| Scheme | Bank of element `e` | Needs |
| --- | --- | --- |
| `cyclic` | `e mod N` | `factor` N |
| `block` | `e / ceil(M/N)` (consecutive chunks) | `factor` N, known size M |
| `complete` | `e` (every element is its own bank) | known size M |

**Pointer arguments** carry no size, so describe them on the function:

```llvm
define void @k(ptr %A) !hls.partition.args !2 { ... }
!2 = !{!3}
!3 = !{!"arg", i32 0, !"scheme", !"block", !"factor", i32 4,
       !"capacity", i64 64, !"elem_bytes", i64 4}
```

Arrays **without** a directive are treated as one single bank (N = 1), so two
accesses to them in the same cycle always conflict. That is the safe
assumption.

The full schema is documented at the top of
[`include/hls-sv/BankPredicate.h`](include/hls-sv/BankPredicate.h).

### On the command line (quick experiments)

```sh
-hls-sv-partition=<name>:<scheme>:<N>[:<M>[:<elem_bytes>]]
```

For example, to try 8 banks without editing the file:

```sh
opt -load-pass-plugin build/HLSSpatialVerify.so -passes='print<hls-spatial-verify>' \
    -hls-sv-partition=A:cyclic:8 -disable-output tests/lit/cyclic_ok.ll
```

## Handing the result to a scheduler

The analysis itself never changes your program. A separate pass,
**`hls-schedule-annotate`**, writes the verdicts into the IR as metadata that a
downstream HLS scheduler can read:

```sh
opt -load-pass-plugin build/HLSSpatialVerify.so -passes=hls-schedule-annotate \
    -pass-remarks-analysis=hls-spatial-verify -S tests/lit/schedule_sequential.ll
```

Every analysed memory instruction gets one of:

```llvm
!{!"parallel",   i32 <group>}
!{!"sequential", i32 <group>, i32 <issue_slot>, !"<status>"}
```

* `group`: the group number shown by `print<hls-spatial-verify>`.
* `issue_slot`: the cycle offset (0, 1, 2, …) the access is serialised to,
  in program order within its group.
* `status`: why it is serialised: `Refuted`, `Unknown` or `Timeout`.

For example:

```llvm
%v0 = load i32, ptr %p0, align 4, !hls.schedule !1
%v1 = load i32, ptr %p1, align 4, !hls.schedule !2
!1 = !{!"sequential", i32 0, i32 0, !"Refuted"}
!2 = !{!"sequential", i32 0, i32 1, !"Refuted"}
```

With `-pass-remarks-analysis=hls-spatial-verify`, each serialised group also
prints a `remark:` line with the reason.

**In C++**, a scheduler reads the metadata through
[`include/hls-sv/SchedulerSignal.h`](include/hls-sv/SchedulerSignal.h):

```cpp
#include "hls-sv/SchedulerSignal.h"

if (auto D = hls_sv::getScheduleDirective(Inst)) {
  // D->Permission, D->Group, D->IssueSlot, D->Status
}

// Or, simply and safely:
hls_sv::SchedulePermission P = hls_sv::effectivePermission(Inst);
```

> **Important:** a memory instruction **without** a directive has *not* been
> proven safe and must be treated as Sequential. `effectivePermission` applies
> that rule for you. This happens, for example, when an array description is
> invalid (`environment error`).

## Command-line options

| Option | Default | What it does |
| --- | --- | --- |
| `-hls-sv-partition=<name>:<scheme>:<N>[:<M>[:<elem_bytes>]]` | – | Set an array's partitioning (overrides metadata; can repeat) |
| `-hls-sv-rlimit=<n>` | 5000000 | Z3 work budget per query. Deterministic: same result on every machine |
| `-hls-sv-timeout-ms=<n>` | 0 (off) | Optional wall-clock limit. Not reproducible; prefer `rlimit` |
| `-hls-sv-refine-pairs` | on | When the whole group is not proven, check each pair to fill the matrix |
| `-hls-sv-max-claims=<n>` | 256 | Larger groups go straight to Sequential |
| `-hls-sv-dump-vc` | off | Print the exact SMT-LIB2 query sent to Z3 |
| `-hls-sv-check-gamma` | on | Sanity-check every partition description before use |
| `-hls-sv-print-at-end` | off | Print verdicts at the end of a normal `-O2`/`-O3` pipeline |

Pass names: `print<hls-spatial-verify>` (print verdicts),
`hls-spatial-verify` (compute and cache them),
`hls-schedule-annotate` (write `!hls.schedule` metadata).

## Running the tests

```sh
ctest --test-dir build --output-on-failure
```

This runs:

* **Unit tests** (`build/HLSSVUnitTests`): the memory model, the bank
  predicates, the SMT translation, the permission mapping and the metadata
  reader.
* **lit tests** (`lit -v build/tests/lit`): one small program per scenario,
  each checked against the expected verdict.

| Test | Scenario | Expected |
| --- | --- | --- |
| `cyclic_ok` / `cyclic_conflict` | `A[i..i+3]`, 4 vs 2 cyclic banks | Parallel / Sequential |
| `block_ok` / `block_conflict` | block partitioning, far apart vs adjacent | Parallel / Sequential |
| `complete_ok` | complete partitioning, 8 constant indices | Parallel |
| `multidim` | `B[x][0..7]` on a 2-D array | Parallel |
| `nonaffine_conflict` | `A[x*y]` and `A[x*y+4]` | Sequential |
| `undecidable_fallback` | hard non-linear indices, tiny budget | Timeout → Sequential |
| `guarded` | same bank, but in different `if`/`else` branches | Parallel |
| `vector` | one `<4 x i32>` load, 4 vs 2 banks | Parallel / Sequential |
| `unresolved` | pointer chosen by `select` between two arrays | Sequential |
| `rmw_collapse` | `A[i] = A[i] * 3` | Sequential (by design) |
| `gamma_error` | pointer argument without a size | Sequential |
| `monolithic` | array without partitioning | Sequential |
| `schedule_parallel` / `schedule_sequential` | `!hls.schedule` metadata and remarks | – |

## Good to know (limitations)

* **Run it after unrolling.** The tool checks the accesses that exist in the
  IR it sees; it does not unroll loops itself.
* **Read-modify-write is always Sequential.** `A[i] = A[i] * 3` reads and
  writes the same element, and a single-port bank cannot do both in one cycle.
  This is intended (paper §4.2); finer-grained permissions are future work.
* **"Sequential" does not mean "wrong".** It means "not proven safe". Timeouts
  and unknown pointers also give Sequential, so the hardware is slower but
  correct.
* **Unknown pointers** (chosen at run time, loaded from memory, or passed to a
  function call that touches memory) make the whole group Sequential, because
  they could hit any bank.
* **Accesses wider than one element** (for example a 64-bit load from an
  `i32` array) could straddle two banks, so they are reported as unresolved.
